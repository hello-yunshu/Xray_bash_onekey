## هدف پروژه

این پروژه یک اسکریپت استقرار و بهرهبرداری Xray است که با Bash نوشته شده است. نصب، گواهیها، فرانتاند Nginx، پیکربندی کلاینت، مدیریت سرویس، پشتیبانگیری و بازیابی، و عیبیابی روزمره را در یک منو جمع میکند و برای کاربرانی مناسب است که میخواهند سریع یک پروکسی تکسروری راهاندازی کنند بدون اینکه کل پیکربندی را دستی نگهداری کنند.

اسکریپت پیکربندی را میسازد و سرویسها را هماهنگ میکند، در حالی که Xray خود پروکسی را انجام میدهد. حالتهای Reality و TLS با فرانتاند Nginx بهتر کار میکنند. هر نوشتن حساس پیش از اجرا با بررسی نحوی یا پشتیبانگیری همراه است و در صورت خطا تا حد امکان بازگردانی میشود تا سرویس در حال اجرا نیمهکاره نماند.

## قابلیتها

| قابلیت | توضیح |
|---|---|
| حالتهای نصب | Reality + Nginx، Nginx + TLS، ws/gRPC/xHTTP ONLY، گره ترانزیت، Docker |
| پروتکلهای انتقال | WebSocket، gRPC و xHTTP، بهصورت جداگانه یا ترکیبی `ws+gRPC+xHTTP` |
| شبکه دوپشته | خروجی IPv4/IPv6 را تشخیص میدهد، رکوردهای A/AAAA دامنه را جداگانه بررسی میکند و ورودیهای کلاینت متناظر را میسازد |
| خروجی کلاینت | لینکهای اشتراک، QR code و پروفایل Clash؛ Clash فعلاً از xHTTP پشتیبانی نمیکند |
| مدیریت امنیت | fail2ban، مسدودسازی ترافیک، SNI Guard، فایروال و مدیریت گواهی |
| عملیات روزانه | مدیریت سرویس، تغییر پیکربندی، پاکسازی گزارشها، مشاهده ترافیک پورت، پشتیبانگیری و بازیابی |
| آمار ترافیک | خواندن بایتهای بالارو، پایینرو و کل برای هر inbound، همراه با JSON، بازنشانی و بهروزرسانی زنده |
| دستیار هوشمند | دستیار محلی RillML برای پایش، تشخیص و پیشنهاد رفع مشکل |
| نگهداری | بهروزرسانی اسکریپت، Xray، Nginx و گواهیها، با پشتیبانگیری و بازگردانی در تغییرات حساس |

## سیستمهای پشتیبانیشده

| سیستم | نسخه | توضیح |
|---|---|---|
| Debian | 12، 13 | از `apt` استفاده میکند؛ CI شامل `debian:12-slim` و `debian:13-slim` است |
| Ubuntu | 24.04، 26.04 | از `apt` استفاده میکند؛ CI شامل `ubuntu:24.04` و `ubuntu:26.04` است |
| CentOS Stream | 10 | از مدیر بسته RPM استفاده میکند؛ CI شامل `quay.io/centos/centos:stream10` است |
| Rocky / AlmaLinux | 10+ | مانند خانواده RPM رفتار میشود؛ نسخه اصلی باید دستکم 10 باشد |

اسکریپت به root، systemd، IP عمومی و دسترسی خروجی شبکه نیاز دارد. نصب بهطور خودکار وابستگیهایی مانند `curl`، `jq`، `openssl`، `qrencode` و `nmap` را تأمین میکند. حالتهای Reality/TLS همچنین به دامنهای با رکوردهای A و/یا AAAA صحیح برای شبکه سرور نیاز دارند.

> سیستمهای پشتیبانی نشده پیش از نصب رد میشوند. قالبهای CentOS تفاوت زیادی دارند؛ در صورت بروز مشکل کامپایل یا وابستگی، از Debian یا Ubuntu استفاده کنید.

## شروع سریع

یک سرور Linux پشتیبانی شده آماده کنید و فرمان زیر را با کاربر root اجرا کنید:

```bash
bash <(curl -fsSL https://github.com/hello-yunshu/Xray_bash_onekey/releases/latest/download/install.sh)
```

پس از پایان نصب، `idleleo` را اجرا کنید تا منوی مدیریت باز شود. میتوانید مستقیماً `idleleo --install-reality`، `idleleo --install-tls` یا `idleleo --install-none` را برای حالت مورد نظر اجرا کنید.

در نخستین استفاده، جادوگر نصب را دنبال کنید و برای موارد نامشخص Enter بزنید تا مقدار پیشفرض پذیرفته شود. پس از نصب، کلاینت را با لینک اشتراک یا QR code که اسکریپت چاپ میکند پیکربندی کنید.

## حالتهای نصب

| حالت | کاربرد | نکات کلیدی |
|---|---|---|
| Reality + Nginx | ورودی پیشنهادی برای یک سرور | در صورت نیاز میتوان پروتکلهای ساده ws/gRPC/xHTTP را برای تعادل بار افزود |
| Nginx + TLS | ورودی استاندارد TLS | گواهیهای Let's Encrypt را خودکار درخواست و تمدید میکند |
| ws/gRPC/xHTTP ONLY | گره بکاند یا تعادل بار | بدون TLS؛ بهطور پیشفرض فقط روی `127.0.0.1` گوش میدهد |
| گره ترانزیت | انتقال TCP مستقل | از Nginx Stream برای انتقال به یک مقصد استفاده میکند و Xray نصب نمیکند |
| Docker | استقرار کانتینری | تصویر شامل Xray، Nginx و اسکریپت اصلی است |

هنگام نصب حالت ws/gRPC/xHTTP، یکی از `ws`، `gRPC`، `xHTTP` یا `ws+gRPC+xHTTP` را انتخاب کنید. اسکریپت برای هر انتقال پورت، مسیر، لینک اشتراک و QR code میسازد. پروفایل Clash از xHTTP صرفنظر میکند و اسکریپت هشدار میدهد.

## آمار ترافیک Xray

پس از روشن شدن آمار، API آمار بهطور پیشفرض فقط روی `127.0.0.1:10085` گوش میدهد. خواندن توسط اسکریپت مستقل `/etc/idleleo/scripts/xray_stats.sh` با مجوز `0600 root:root` انجام میشود. اسکریپت اصلی فقط ورودی، دانلود، بررسی SHA256 و واگذاری را انجام میدهد و منطق پرسوجو را تکرار نمیکند.

```bash
idleleo --stats                  # جدول: بالارو، پایینرو و کل برای هر inbound
idleleo --stats --json           # JSON قابل خواندن توسط ماشین
idleleo --stats-reset            # پاک کردن شمارندهها پس از تأیید تعاملی
idleleo --stats-reset --yes      # تأیید برای خودکارسازی
idleleo --stats-watch 5          # بهروزرسانی هر 5 ثانیه؛ Ctrl-C خارج میشود
```

اگر اسکریپت آمار موجود نباشد، اسکریپت اصلی `xray_stats.sh` را از Release فعلی دانلود میکند و با `statsScriptSha256` از `release-manifest.json` بررسی میکند. خطای بررسی فقط بر خواندن اثر دارد و بر کلید آمار اثری ندارد. اگر آمار روشن باشد اما `api.listen` وجود نداشته باشد، نخستین اجرای `--stats` صریحاً میپرسد آیا باید آن را اضافه و Xray راهاندازی مجدد شود؛ رد کردن، پیکربندی را تغییر نمیدهد.

### کدهای خروج

| کد خروج | معنا |
|---|---|
| `0` | پرسوجو موفق بود؛ شمارنده صفر نیز موفق است |
| `1` | کاربر بازنشانی را لغو کرد |
| `2` | پیشنیاز موجود نیست: آمار خاموش، بدون `api.listen`، Xray در حال اجرا نیست، API در دسترس نیست، اسکریپت نیست یا بررسی شکست خورد |
| `3` | فراخوانی API یا تجزیه JSON شکست خورد |
| `4` | آرگومان نامعتبر |
| `5` | کاربر root نیست یا مجوز کافی ندارد |
| `130` | پایش با Ctrl-C قطع شد |

در خطا هرگز صفر جعلی چاپ نمیشود: آمار خاموش یا API در دسترس نبودن `2` برمیگرداند، JSON خراب `3` و کاربر غیر root `5`.

### مرز امنیتی

> API آمار فقط به loopback متصل میشود اما احراز هویت ندارد. سایر کاربران محلی از نظر تئوری میتوانند به پورت دسترسی داشته باشند و شمارندهها را بخوانند یا بازنشانی کنند. آن را روی VPS تککاربره استفاده کنید و هرگز `10085` را در اینترنت باز نکنید؛ `--stats-reset` همیشه تأیید صریح میخواهد.

Xray StatsService فقط شمارندههای بالارو/پایینرو inbound و Uptime را ارائه میدهد و **تعداد اتصالهای فعال را ارائه نمیدهد**. برای تعداد اتصال از ابزارهای سیستمی یا راهکار مشاهدهپذیری جداگانه استفاده کنید و انتظار نداشته باشید `--stats` آن را نشان دهد.

## پشتیبانگیری و بازیابی

`idleleo --backup` فقط فایلهای مدیریتشده توسط اسکریپت را پشتیبان میگیرد: `/etc/idleleo`، `/usr/local/nginx`، باینری Xray، unitهای systemd، crontab root و وضعیت ACME. این پشتیبان کامل میزبان نیست و دادههایی که در مسیرهای دیگر گذاشتهاید بهطور خودکار 포함 نمیشوند.

`idleleo --restore` پشتیبانی با جدیدترین timestamp را انتخاب میکند. پشتیبانهای دارای مانیفست checksum، SHA256 هر فایل آرشیو را بررسی میکنند و پیکربندی مدیریتشدهای را که در پشتیبان نیست حذف میکنند؛ پشتیبانهای قدیمیتر بدون مانیفست فقط بررسی ساختاری میشوند و پاکسازی بین حالتها را انجام نمیدهند. فایلهای ساختهشده توسط کاربر نگه داشته میشوند و سرویسها خودکار راهاندازی نمیشوند. پس از بازیابی بین حالتها، پیکربندی باقیمانده را بررسی و در صورت نیاز سرویسها را راهاندازی مجدد کنید. اگر پشتیبان قدیمی پیوند نمادین `/usr/local/share/xray` را نداشته باشد، بازیابی آن را می‌سازد یا پوشه قدیمی GeoData را در `/etc/idleleo/share/xray` ادغام می‌کند و سپس با `xray run -test` واقعی بررسی می‌کند؛ اگر خودتعمیری ناموفق باشد بازگردانی می‌شود، بنابراین پشتیبان‌های قدیمی بدون نصب مجدد روی میزبان جدید بازیابی می‌شوند.

آرشیوهای پشتیبان ممکن است گواهی، کلید خصوصی و پیکربندی کلاینت داشته باشند. آنها را فایل حساس بدانید و در مکان عمومی بارگذاری نکنید.

## بهروزرسانی و نگهداری

از «جادوگر بهروزرسانی ← بهروزرسانی اسکریپت» در منوی مدیریت بهروزرسانی کنید یا اجرا کنید:

```bash
idleleo --update                  # تأیید تعاملی
idleleo --update --yes            # غیرتعاملی، تأیید خودکار در همان سری انتشار
idleleo --update --yes --allow-major  # بهروزرسانی بین سریها؛ برداشتن صریح محدودیت
```

`--yes` فقط بهروزرسانیهای همان سری انتشار را خودکار تأیید میکند؛ عبور از سریها به `--allow-major` نیز نیاز دارد. `--allow-major` فقط محدودیت سری را برمیدارد و جایگزین تأیید نیست، بنابراین در حالت غیرتعاملی همچنان `--yes` لازم است. بهروزرسانی اسکریپت، `/etc/idleleo/install.sh` را یکجا جایگزین میکند، نشانیهای Release را برای اسکریپت جدید بازمحاسبه میکند و داراییهای کمکی را همگام میکند.

`--xray-update` فقط هسته Xray و `--nginx-update` فقط Nginx را بهروزرسانی میکند؛ هیچیک اسکریپت را بهروزرسانی نمیکند. بهروزرسانی خودکار اسکریپت فقط در همان سری انتشار انجام میشود؛ بهروزرسانی خودکار Xray و Nginx همچنان از فراداده API پیروی میکند. پیش از بهروزرسانی `idleleo --backup` را اجرا کنید.

حالت قدیمی XTLS دیگر ورودی نصب یا نصب مجدد ندارد. سرویسهای XTLS موجود میتوانند به کار ادامه دهند، اما اسکریپت نمیتواند آنها را دوباره نصب یا حالت را عوض کند. برای ادامه مدیریت، ابتدا پشتیبان بگیرید و حذف کنید، سپس Reality، TLS یا حالت ترانزیت را دوباره مستقر کنید.

## پیکربندی مجدد

وقتی نصبکننده دوباره روی سیستم نصبشده اجرا میشود، پیکربندی در حال اجرا را خودکار پشتیبان میگیرد و سه مسیر پیشنهاد میکند:

| مسیر | توضیح | محدودیت |
|---|---|---|
| حفظ پیکربندی و استقرار مجدد | routing، outbounds، DNS و پیکربندی چندکاربره سفارشی را نگه میدارد و فقط فیلدهای انتخابی را تغییر میدهد | تغییر ساختار انتقال مانند ws به gRPC را پشتیبانی نمیکند |
| بازسازی از قالب استاندارد | قالب استاندارد را از پارامترهای قابل استفاده مجدد میسازد | routing، outbounds و DNS سفارشی ممکن است حذف شوند |
| تغییر حالت | تغییر به حالت پروتکل دیگر، مثلاً Reality به TLS | بهطور پیشفرض فقط UUID/email کاربر اصلی را بازاستفاده میکند؛ سایر کاربران منتقل نمیشوند |

اگر هر مرحله شکست بخورد (نوشتن پیکربندی، راهاندازی سرویس، بررسی سلامت و غیره)، اسکریپت به پیکربندی اصلی پشتیبانگیریشده بازمیگردد. پوشههای پشتیبان از timestamp یکتا استفاده میکنند تا پیکربندیهای مجدد پشتسرهم تداخل نکنند.

## مهاجرت به مدیر Go (آزمایشی)

> سطح شواهد: `CONTAINER_VERIFIED` در سطح کانتینر (Ubuntu 24.04 با digest ثابت و systemd/Xray/nginx واقعی)، **نه «تأییدشده روی VPS واقعی»**. صدور/تمدید واقعی ACME در این دوره بررسی نمی‌شود.

- **نسخه فعلی Go را فعال نمی‌کند و هرگز مهاجرت را پیشنهاد نمی‌دهد**: نصب تازه، `-u`، `auto_update`، نصب مجدد کامل و منو هرگز Go را بررسی، دانلود یا ذکر نمی‌کنند؛ کاربران عادی هیچ نقطه ورود مهاجرتی نمی‌بینند. کد مهاجرت فقط برای نسخه‌های بعدی نگه داشته شده و تنها با پارامتر داخلی `--internal-bridge-offer` در زمان بررسی نگهدارندگان قابل دسترسی است.
- **مراحل مهاجرت**: SHA256 باینری نامزد + بررسی ELF → ممیزی فقط‌خواندنی و خلاصه کامل تغییرات → snapshot/journal → پیش‌بررسی `xray -test` / `nginx -t` → جابه‌جایی اتمی `/usr/bin/idleleo` → حذف دقیق ۴ ورودی cron پروژه → نصب `idleleo-schedule.timer`.
- **موارد حفظ‌شده**: پیکربندی `/etc/idleleo`، گواهی‌ها و کلیدهای خصوصی، کاربران، cron تعریف‌شده توسط کاربر، قطعه‌های nginx سفارشی.
- **بازگردانی**: هر مرحله ناموفق توسط `/opt/idleleo/recovery/idleleo-recover` بازیابی می‌شود؛ پس از `COMMITTED` مهاجرت معکوس خودکار انجام نمی‌شود.
- **زمان‌بندی‌ها**: `idleleo schedule status` برای مشاهده و `install` / `remove` / `run` برای مدیریت. بازآوری GeoData و جمع‌آوری آمار به‌صورت بومی (systemd timer) پیاده‌سازی شده‌اند؛ به‌روزرسانی خودکار از کانال انتشار Go استفاده می‌کند و **به `idleleo update configure --manifest-url URL` صریح نیاز دارد**؛ در صورت عدم تنظیم، هر دور `degraded` ثبت می‌شود (منبع حدس زده نمی‌شود و شکست بی‌صدا رخ نمی‌دهد)؛ تمدید گواهی هنوز ACME ندارد و فقط قرارداد اثر انگشت و هشدار انقضا پس از تمدید خارجی ارائه می‌شود.
- **دستورهای Phase 04**: `idleleo update status|check|apply|configure`، `idleleo stats [--json]`، `idleleo service status|start|stop|restart|reload|logs`، `idleleo rill status`. دستورهای سرویس فقط unitهای خودی را مجاز می‌دانند؛ `stats` فقط‌خواندنی است و watch/reset ندارد.
- **قرارداد گواهی**: اثر انگشت DER مبنا ثبت می‌شود و `restart xray` / `reload nginx` فقط با تغییر اثر انگشت انجام می‌شود؛ بدون تغییر راه‌اندازی مجدد نمی‌شود؛ کلید خصوصی خواندنی برای همه reload را رد می‌کند؛ انقضا یا کمتر از ۳۰ روز بدون تغییر `degraded` ثبت می‌کند. **صدور/تمدید/پاکسازی واقعی ACME پیاده‌سازی نشده است.**
- **محتوای سفارشی**: کلیدهای سطح بالای ناشناخته Xray و قطعه‌های nginx سفارشی که ممیزی فهرست می‌کند باید ابتدا دستی تأیید شوند، وگرنه `prepare` با exit 6 رد می‌کند و بازنویسی بی‌صدا انجام نمی‌شود.

## عیبیابی

| نشانه | ابتدا بررسی کنید | پیشنهاد |
|---|---|---|
| نصب رد شد | `/etc/os-release` و ماتریس پشتیبانی | به نسخه سیستم پشتیبانیشده ارتقا دهید یا از Debian/Ubuntu استفاده کنید |
| Xray اجرا نمیشود | `systemctl status xray`، `idleleo --xray-error` | `journalctl -u xray`، پیکربندی و اشغال پورت را بررسی کنید |
| خطای نحوی پیکربندی | `xray run -test -config /etc/idleleo/conf/xray/config.json` | خطا را اصلاح کنید یا با `idleleo --restore` بازگردانی کنید |
| پورت اشغال است | `ss -ltnp` | پورت را آزاد کنید یا از منو پورت شنود را تغییر دهید |
| مشکل گواهی | `idleleo --cert-status` | DNS، پورتهای 80/443 و وضعیت ACME را بررسی و سپس `idleleo --cert-update` را اجرا کنید |
| تعارض با Nginx موجود | `/usr/local/nginx/sbin/nginx -V`، `systemctl status nginx` | با Nginx نصبشده توسط LNMP یا اسکریپتهای مشابه مخلوط نکنید؛ ابتدا تعارض را برطرف کنید |
| آمار `2` برمیگرداند | کلید آمار، وضعیت Xray، `127.0.0.1:10085` | آمار را روشن کنید، Xray را راهاندازی کنید یا `api.listen` را بررسی کنید |
| آمار `3` برمیگرداند | پاسخ API و ساختار JSON | گزارشها و پیکربندی Xray را بررسی و دسترسپذیری StatsService را تأیید کنید |
| آمار `5` برمیگرداند | کاربر فعلی | با root اجرا کنید یا مجوز فایلها را بررسی کنید |
| Clash گره ندارد | نوع پروتکل | Clash از xHTTP پشتیبانی نمیکند؛ از کلاینت سازگار استفاده کنید |

گزارشها و عیبیابی: `/etc/idleleo/logs/`، `/var/log/xray/`، `idleleo --show`، `idleleo --xray-access` و `idleleo --xray-error`.

## پرسشهای متداول

**آیا آمار تعداد اتصالهای فعال را نشان میدهد؟** نه. StatsService فقط شمارندههای بالارو/پایینرو inbound و Uptime را ارائه میدهد و تعداد اتصال را نمیدهد.

**کاربران Cloudflare چه زمانی CDN را روشن کنند؟** CDN را تنها پس از تأیید نصب، گواهیها و اتصال مستقیم روشن کنید. در غیر این صورت پروکسی CDN میتواند صدور گواهی را مختل کند.

**آیا IPv4 و IPv6 همزمان قابل استفادهاند؟** بله. اسکریپت توان خروجی عمومی را تشخیص میدهد و رکوردهای A/AAAA دامنه را جداگانه بررسی میکند. در محیط دوپشته رکوردهای A و AAAA را درست تنظیم کنید.

**چگونه پورت، UUID یا انتقال را تغییر دهم؟** «تغییر پیکربندی» را در منو باز کنید یا جادوگر نصب را دوباره اجرا و مسیر پیکربندی مجدد را انتخاب کنید. برای تغییر ساختار انتقال از بازسازی قالب استاندارد استفاده کنید.

**چگونه حذف کنم؟** `idleleo --purge` را اجرا کنید. پیش از حذف `idleleo --backup` را اجرا کنید و تصمیم بگیرید پیکربندی و گواهیها را نگه میدارید یا نه.

**الزامات نگاشت رشته سفارشی به UUID چیست؟** اسکریپت از نگاشت UUIDv5 استفاده میکند که به پشتیبانی کلاینت نیاز دارد. اگر کلاینت پشتیبانی نمیکند، از UUID استاندارد استفاده کنید.

**آیا میتوان مستقیم در محیط تولید استفاده کرد؟** ابتدا در محیط آزمایشی اتصال، تمدید گواهی، پشتیبانگیری/بازیابی و مسیر بهروزرسانی را بررسی کنید و سپس در تولید استفاده کنید.

## نکات امنیتی

- API آمار فقط به `127.0.0.1` متصل میشود و احراز هویت ندارد. `10085` را در اینترنت باز نکنید و نگذارید کاربران محلی غیرقابلاعتماد به آن دسترسی داشته باشند.
- حالت Reality + Nginx بهطور پیشفرض SNI Guard را فعال میکند: SNI ناشناس، SNI خالی و TLS غیرعادی هرگز به بکاند Xray Reality نمیرسند؛ بهطور پیشفرض جداسازی `ssl_reject_handshake` استفاده میشود.
- Fail2ban، فایروال و مسدودسازی ترافیک تقویتهای اختیاری هستند. پیش از فعالسازی مطمئن شوید دسترسی مدیریتی خودتان را قفل نمیکنند.
- آرشیوهای پشتیبان، گواهیها و پیکربندی کلاینت اطلاعات حساس دارند. مجوز فایلها را محدود کنید و آنها را عمومی به اشتراک نگذارید.
- اسکریپت به root نیاز دارد؛ پیش از تأیید کارکرد آن را در تولید استفاده نکنید.

## Docker و AI Skill

تصویر Docker شامل Xray، Nginx و اسکریپت اصلی است و قابلیتهای اسکریپت داخل کانتینر در دسترساند. [راهنمای استقرار Docker](https://github.com/hello-yunshu/Xray_bash_onekey/blob/main/docker/DOCKER.md) را ببینید.

```bash
git clone https://github.com/hello-yunshu/Xray_bash_onekey.git
cd Xray_bash_onekey
docker compose up -d
docker attach xray-onekey
```

AI Skill به ابزار AI دارای پشتیبانی Skills اجازه میدهد استقرار را بدون پاسخ به هر پرسش تعاملی خودکار انجام دهد. [Xray_bash_onekey_skill](https://github.com/hello-yunshu/Xray_bash_onekey_skill) را ببینید.

اسکریپت از Reality، TLS، ws/gRPC/xHTTP ONLY و گره ترانزیت Nginx Stream پشتیبانی میکند. قالبهای استقرار خودکار AI Skill در حال حاضر فقط Reality و TLS را پوشش میدهند؛ برای ws/gRPC/xHTTP ONLY و گره ترانزیت از idleleo روی سرور استفاده کنید.

## دستیار عملیات RillML Xray AI

RillML (به اختصار Rill) بهرهبرداری محلی و سازگار برای Xray فراهم میکند: پایش زنده سلامت Xray/Nginx، تشخیص خودکار خطا و پیشنهاد رفع مشکل بدون API خارجی. در منوی اصلی `9` را وارد کنید یا `idleleo --rill-agent` را اجرا کنید.

| عمل | فرمان |
|---|---|
| باز کردن منوی دستیار AI | `idleleo --rill-agent` |
| نصب یا تعمیر موتور تصمیم AI | `idleleo --rill-agent-install` |
| نمایش وضعیت تصمیم AI | `idleleo --rill-agent-status` |
| اجرای تشخیص خطای AI | `idleleo --rill-agent-diagnose` |
| بررسی موتور تصمیم AI | `idleleo --rill-agent-verify` |
| غیرفعالسازی ایمن تصمیم AI | `idleleo --rill-agent-safe-disable` |
| حذف موتور Rill AI | `idleleo --rill-agent-uninstall` |

Rill بهطور پیشفرض بر پیشنهادهای تشخیصی تمرکز دارد و پیش از فعالسازی تغییرات خودکار سیستم را تغییر نمیدهد.
