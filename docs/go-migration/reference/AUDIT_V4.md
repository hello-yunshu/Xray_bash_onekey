# Xray Go v4 开发 ZIP 独立审计报告（含复现证据）

> 审计日：2026-11-06。对象：`Xray_Go_深度审计_迁移实测_五阶段计划_v4_2026-11-06.zip`。SHA256：`0bdcb1c48863f11e7d770edc9e3d88c816c50b04b0e9b3e4e021a93ab75d1389`。
> 审计方式：解包逐项文件检查、包内 SHA256 校验、重跑 `go test -race` / `go vet`、运行原迁移脚本、额外独立失败注入；并复核五个阶段的职责与演示实现的差距。本轮**不**修改 GitHub 和生产 VPS。

## 一、总体判定

- **ZIP 交付完整性：通过。** 24 个文件、目录无 `../` / 绝对路径越界、包内 `SHA256SUMS.txt` 全部匹配、五阶段 MD 均存在。
- **原型既有测试：通过。** 16/16 Go 原测试成功，Race、Vet 通过，原有 Reality/Relay 合成演示通过。但“已有测试绿灯”与“迁移机制已达到生产安全”是两回事。
- **产品与五阶段定位：基本一致。** 保持 Go 唯一正式管理器、CLI 优先、保留旧运行路径、手动迁移、禁止自动升级触发 Go 下载、首版不强做 sing-box/Web。
- **迁移原型可靠性：不合格，禁止当作生产 Bridge。** 本报告有 3 个可重现的 P0 级安全边界缺陷；v4 代码没有提供真正的候选程序自检、入口漂移保护和恢复时冲突保护。
- **功能完成度：仅演示级。** 包内 F01–F28 与 M01–M16 是未来验收约束，**不是**已实现项目功能；目前没有真实 systemd、Xray/Nginx、ACME、cron、Rill 的完整迁移验证。

## 二、实测复现的三个缺陷（全部有独立 Go 失败用例）

| ID | 等级 | v4 位置 | 重现结果 | 改进要求 |
|---|---|---|---|---|
| V4-P0-01 | P0 | `probe/bridge/bridge.go:404–410`，`Activate` | 仅检查文件为普通文件且可执行。`TestAuditExecutableTextAcceptedAsGoCandidate` 提交了并非 Go 二进制的可执行文本为正式 Go 管理器，结果为 `COMMITTED` | 要求候选预期 SHA256、ELF/架构或运行时真实自检、功能预验收；SHA 的上游可信发行来源要单独验证 |
| V4-P0-02 | P0 | `probe/bridge/bridge.go:378–428` | `Prepare` 后另一个参与者修改旧管理入口；`Activate` 只查两份源配置 SHA、不查入口快照，直接覆盖改动后的入口并提交 | `PREPARED` 时记录入口身份与摘要，激活前再次验证，冲突立即拒绝 |

## 三、其它重要缺陷与工程约束

| ID | 等级 | 依据 | 建议 |
|---|---|---|---|
| V4-P1-04 | P1 | v4 `Prepare` 先写 manager 配置再写 Journal（347–353 行） | 进程在两次写入之间死亡可能留下“已有新管理配置、却无 Journal”的孤儿状态；Journal 必须在首个副作用前进入 `PREPARING`，恢复需处理部分落盘 |
| V4-P1-05 | P1 | v4 Journal `EntrypointOldBytes []byte`（47–52、331–337 行） | 普通入口全部字节被 Base64 放进 Journal；移至独立 `0600` 快照，Journal 只存 SHA、原模式、路径和恢复状态 |
| V4-P1-06 | P1 | v4 `Prepare/Activate/Recover` 没有跨进程排他锁 | 两次独立迁移可并发执行、覆盖同一记录；引入排他锁并明确定义与现有 Bash 共享 update lock 的生产契约 |
| V4-P1-07 | P1 | v4 `ReadStatus` 强制读取 manager 配置（474–495 行） | 回滚后删除 manager 配置，反而无法正常展示 `ROLLED_BACK`；状态查询应以 Journal 为主，manager 可以缺失 |
| V4-P1-08 | P1 | v4 的 `root/.idleleo-probe-sandbox` 仅为安全演示标记 | 标记不能代替正式生产的路径和设备归属保护；**不能直接删掉标记后部署在 VPS 上** |
| V4-P1-09 | P1 | v4 原型只检查旧 `install_config.json` 和单个 runtime JSON 或 relay 片段 | 不能据此判断证书、服务单元、cron、当前 Xray 账户、Rill、Nginx include、IPv6 全链路兼容；必须作为 Phase 03 的现场预检 |
| V4-P1-10 | P1 | v4 `run_migration_trial.sh` 测试“候选”只在激活前复制（`Prepare` 不绑定候选版本和摘要） | 将候选版本/摘要纳入持久快照，执行真实 Go 预检，通过后才允许进入 `ACTIVATING` |
| V4-P2-11 | P2 | v4 原始 sandbox 的旧 `/usr/bin/idleleo` 是绝对 `/etc/idleleo/install.sh` 链接 | 在隔离沙盒外指向真实宿主路径；原脚本只检查恢复链接文本，**没有证明旧 Bash 入口真的可运行**。新试验使用等价相对路径并执行验证 |
| V4-P2-12 | P2 | 五阶段文档与实际 16 项原型单测 | 实施契约中需要将演示可验证范围与生产验收逐项区分，不得把“16 个 Go 测试”代替未来 M01–M16 的实际 CLI/SSH/cron 验收 |

## 四、开发阶段文档审计

| 阶段 | 当前可取之处 | 尚未闭环的部分 |
|---|---|---|
| 00 基线与契约 | F01–F28、R01–R24、有约束的系统资源归属、双发行通道 | 还没有由当前仓库代码自动提取的 CLI 完整分发表；GitHub 上真实 Stats Ubuntu 失败根因仍待日志；实际旧配置版本矩阵尚无测试样本 |
| 01 Go 核心 | 配置只读 / 文件事务 / 无常驻服务设计正确 | 原型无法代替正式事务库：多资源恢复、账户权限、真实命令执行器仍未实现；应加入入口/候选 hash、恢复冲突保护 |
| 02 Xray 全能力 | 明确 Reality 主次负载与 relay 分别实现，多用户/shortId/自定义 JSON 列明 | F01–F28 仍是**计划**；需要真实 Xray `run -test`、Nginx `-t`、系统服务、stats JSON、证书续期和容器实测，不能以本 ZIP 测试替代 |
| 03 Bridge | 明确手动 TTY 同意、自动更新不能下载 Go、独立恢复器 | Bridge-aware Bash 版本尚未实现；缺失真实 cron、systemd、发布元数据的切换/恢复代码；现有原型的 3 项 P0 必须先消除 |
| 04 验收发布 | 发行版 / ARM / Docker / CI 红灯均设验收要求 | 当前没有 Go 生产 Release / 真实 VPS 恢复证据；旧 Stats Ubuntu 红灯尚未根因定位，不得宣布可发布 |

## 五、建议修正优先级

1. **立即修复 Go 原型安全边界**：候选身份、入口漂移、恢复冲突、首个副作用前 Journal、独立快照与锁（本包 v2 已对沙盒逻辑演示）。
2. **Phase 00 先固定外部发布信任链**：Go 资产名称、架构、Hash、签发信息从可信固定 Release 获得，不能只是从与二进制相同的可篡改源取得 SHA；老 Bash 下载字段不能混入 Go。
3. **Phase 01 最小核心**：把上述边界转化为真实 `change`/`bridge` 共享原语；只读命令不能隐式修复，且缺配置时仍可离线查看帮助。
4. **Phase 02 真业务**：先把配置写入与服务状态恢复做完，再做复杂用户/中转等模式，必须真实执行校验器而非只测 JSON 结构。
5. **Phase 03 实机迁移**：连通手动 Bash TTY 同意→固定 Bridge 发行物→真实可用 Go→精确 cron 交接→独立恢复器，必测 `SIGKILL`/重启/低磁盘/数据漂移。
6. **Phase 04 发布门禁**：必须消除旧 CI Ubuntu Stats 未知红灯，或明确作为阻断 Go 发行的未解决基线，不得跳过相关 Job。

## 六、审计边界（不可夸大）

- 本次实测的是 **ZIP 内代码**，不等于完成了远程 `main` 最新版本全部 253 个文件的逐行审计；没有生产 SSH 或系统级权限。
- 旧 ZIP 内部 `SHA256SUMS.txt` 与 ZIP 同源，只证明 ZIP 内文件**一致性**，不是第三方签名或来源真实性。
- 本报告没有声称原有三处安全缺陷已经存在于用户生产 Bash；它们明确位于 **v4 附带的 Go 迁移原型**。Bash 现存问题仍以 v4 原报告为独立依据。
- v2 沙盒原型亦**不能生产使用**；所有真实服务迁移和发布仍按五阶段计划完成。
